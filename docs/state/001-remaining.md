# Remaining

What this project does not have: decisions not taken, work not done, tools with no specification, and the defects that are known and unfixed. It is the counterpart of [What Is Built](000-what-is-built.md), which is what it does have.

It is a backlog, not a specification. Nothing listed here is decided.

## Pending Decisions

- **Recovery** — what recovery is in this system, which paths there are and what each one is for, and what the recovery system has to be able to do. It is spread today and is the subject of nothing: [Disk Layout](../decisions/001-disk-layout.md) gives it a partition, [Bootloader](../decisions/008-bootloader.md) gives it an entry, [Snapshots](../decisions/004-snapshots.md) runs every restore from it, and [Kernel](../decisions/006-kernel.md) leans on it for a bad update. Two documents defer an obligation to it: [Encryption](../decisions/002-encryption.md) leaves it how the unlock file and the master-key copy are used from there, and [Work Contexts and Accounts](../decisions/000-work-contexts-and-accounts.md) requires root recovery procedures to be documented. The size of its partition follows from what it has to hold.
- **Audio stack** — which daemon is installed and enabled. [What is OpinionatedArch](../general/000-what-is-opinionatedarch.md) names the audio daemon among the choices this project takes for the operator, so a general document promises it while no decision covers it.
- **A `script` operation in the dotfiles map** — a rule that runs a script instead of producing a target. It is what would install an AUR package, by hand or through a helper the operator brought, now that nothing in the system reaches the AUR, and it covers what the declarative operations cannot express. What the script is given, what it may touch, where it runs among the other operations and what its failure means are what has to be decided, against the rule [Dotfiles Map Format](../tools/oparch-dotfiles-sync/001-map-format.md) states today: arbitrary commands are forbidden, because a map that executes code stops being data that can be validated as a whole before anything is applied.
- **A preserved home and a named work context that share a name** — in `keep-homes` the operator ticks which homes to keep and names the contexts to create, and [Installer Inputs and Bootstrap Baseline](../tools/oparch-installer/002-inputs-and-bootstrap-baseline.md) says the second are created "in addition to" the first. Nothing says what a name arriving by both paths means. The intended answer is that it is not an error: the context is created as any other, and the subvolume already there stays with the data it holds. What has to be decided is the whole of it — what the tool does with a home whose ownership or modes do not match what a new context is given.
- **Base security policy** — firewall, SSH (if applicable), sudo policy.
- **Rebuilding the return message on an installed system** — nothing is installed for it today. The installer renders from the live medium, so an installation needs nothing on the target; but the tool reads the body of the Plymouth script, and the default template package and theme, from its assets directory, and no assets directory is put on the installed system. Until one is, editing `/etc/opinionatedarch/return-message.yaml` and running the tool again does not work there, although [oparch-return-message-render](../tools/oparch-return-message-render/000-command.md) describes that as the reason the tool exists apart from the installer. Deciding to support it also decides whether the package and theme the operator actually used are kept, and so whether the values file keeps naming where each came from or is rewritten to name local copies.

## Pending Work

- Register the EFI boot entry for `recovery.efi`, which [Boot Image Format](../decisions/007-boot-image-format.md) requires the installation to leave. It waits on the recovery system: there is no image to point an entry at until that system is built, and an entry naming a file that is not there is a menu line that fails when it is chosen.
- **Recovery system** — the Arch installation that lives on the recovery partition [Disk Layout](../decisions/001-disk-layout.md) gives it, with the tools to chroot the installed system and to repair the keys of its container, and with its own mkinitcpio preset building the unified image [Boot Image Format](../decisions/007-boot-image-format.md) requires at `recovery.efi`.
- Build the boot artifacts as [Boot Image Format](../decisions/007-boot-image-format.md) decides them, none of which the installer does today: point the kernel package's mkinitcpio preset at `OpinionatedArch/` so the kernel image and the initramfs are written there, register EFI boot entries for `recovery.efi` and for the netboot binary with the bootloader left first in the boot order, and install three pacman hooks — one moving the microcode image into that directory, one remaking `netbootx64.efi` from the `ipxe` package, and one running `grub-install` again whenever `grub` is updated. The menu's paths move with them: `grub.cfg` loads `/vmlinuz-linux` and `/initramfs-linux.img`, and the installer writes `set ucode_image=/amd-ucode.img` into `oparch.cfg`. GRUB moves with them: `grub-install` is called with `--boot-directory` so its modules, the menu and `oparch.cfg` land in `OpinionatedArch/grub/`, and the comments of `assets/grub/grub.cfg` name the old paths. The order is part of the work — a menu pointing into the directory before anything puts the files there is a machine that does not start. Two documents follow the code when it lands: [Dotfiles Map Format](../tools/oparch-dotfiles-sync/001-map-format.md), whose example and consideration copy a `grub/` directory to `/boot`, and [What Is Built](000-what-is-built.md), which says the machine file is written as `/boot/grub/oparch.cfg` and is true until then.
- Move the return message's margin from the boot to the composition, as [Return Message Theme Format](../tools/oparch-return-message-render/003-theme-format.md) now defines it. The renderer still reads `screen.fit` and writes it into the Plymouth script, the script still scales the composition to that fraction, and the project's own theme in `assets/return-message-theme/manifest.yaml` still declares it; none of them knows `canvas.margin`, which is what the format has instead. What the splash draws has to end up covering the screen, with the space around the text left in the images the renderer composes.
- Generate archiso with the installer and the recovery scripts.
- Pack tools in pacman packages and create the oparch repository.
- Remove `snapper` and `snap-pac`; replace by snapshot manager tools.
- Implement the `keep-homes` install mode. The screen offers it and the configuration file documents it, and `prepare_layout` answers it with `keep-homes install mode is not supported yet.` before touching the disk. The prompt that goes with it is missing too: which of the existing home subvolumes to preserve. [Installer Inputs and Bootstrap Baseline](../tools/oparch-installer/002-inputs-and-bootstrap-baseline.md) lists it, and the configuration file already carries it as `preserved_work_contexts`, so a file can express what no screen asks.
- Put on the project's ISO, and on the installed system, what the tools require and the official Arch medium does not carry: `imagemagick`, `pango`, `noto-fonts`, `fontconfig` and `git`. Which tool needs which, and what each has to be able to do, is the `Requirements` section of [oparch-installer](../tools/oparch-installer/000-command.md) and [oparch-return-message-render](../tools/oparch-return-message-render/000-command.md); the work here is putting them there. Until then the end-to-end harness installs them in the guest by hand, which [End-to-End Testing](../development/006-end-to-end-testing.md) records as a step that disappears when the ISO arrives. One of them has never been observed failing: whether the drawing actually breaks without `pango` is unknown, because the run that went looking failed earlier, on a live environment too old for the ImageMagick its mirrors offered.
- Write the operational tools. `oparch-installer`, `oparch-return-message-render` and `oparch-dotfiles-sync` exist; the seven specified in `../tools/` that are not those have no implementation at all. `oparch-work-context-create`, `oparch-work-context-remove` and `oparch-password-rotate` had one in `sh`, written before the language was decided and under the names the tools carried then, along with two snapshot scripts; all of them were deleted rather than carried, because a tool half-written in a language the project no longer uses is worse than one not written yet — it is found and run. Every built-in tool is written in the language [BAML as Implementation Language](../development/000-baml-as-implementation-language.md) decides, and whether each needs a host is answered the same way as for any other, in [Host Bridge](../development/001-host-bridge.md). The installed system therefore has no account, password or snapshot tooling on it today, which is what makes this the first work rather than merely pending.
- Run the end-to-end harness against the dotfiles step, and write the four cases it is missing. [End-to-End Testing](../development/006-end-to-end-testing.md) describes five; only the first is written, and it has never been executed. The run [What Is Built](000-what-is-built.md) records is the harness as it was before the dotfiles step was given to it, so nothing has yet run the harness in the shape it is in now. The other four are a repository that stays one, a map whose secrets arrive, a package that does not hold what it declares, and a passphrase that does not open the store. Three of them are runs that are meant not to happen, and the harness performs one installation per invocation, so covering them is a change to its shape rather than four more assertions.
- Check an installed machine against [Dotfiles](../decisions/014-dotfiles.md). The dotfiles step has been exercised by hand as far as its targets landing, but what it leaves `/dotfiles` as has not been looked at on a booted system: the modes under it, the default ACL, whether a work context can write there, and whether git works in it without complaining about who owns it. The same for the secret store's own `0700` and `0600`. [Installation Checks](../development/007-installation-checks.md) lists all of them; none has been observed.
- Look again at the `Secrets` port, now that the toolchain carries [`baml.crypto`](https://github.com/BoundaryML/baml/pull/4431). [Host Bridge](../development/001-host-bridge.md) makes that port the one exception that crosses to the host, on the grounds that the standard library carries no cryptography of any kind, and says the implementation moves the day BAML grows some; this is that day arriving in part. The module brings an `Aead` interface with AES-256-GCM-SIV, AES-128-GCM-SIV, ChaCha20-Poly1305 and XChaCha20-Poly1305, a `Hasher` with SHA-256, and key generation. It is not all of what opening the store takes. [Secret Store Archive](../tools/oparch-dotfiles-sync/002-secret-store-archive.md) makes the store an `age` passphrase file, where `scrypt` derives the key and ChaCha20-Poly1305 seals the payload, and the module carries that cipher but no key derivation and nothing of the format — header, stanzas, HMAC, chunked payload — which is what the `age` crate does for the host today in `src/installer/host/src/main.rs`. So what is open is how much of the opening can move into BAML and whether the port stays for whatever cannot.
- Format the BAML sources with the formatter the toolchain now ships. `baml pack` warns that the code is unformatted, and it is: `baml fmt` rewrites every file, including ones nothing has touched — `phase_disk.baml` alone changes 452 lines — because what the formatter does with multi-argument signatures, chained calls and long argument lists changed between `0.15.1` and `0.17.1`. It is one mechanical commit, and it is its own commit precisely because it touches everything and would bury any change it travelled with.
- Replace what is left of "shared configuration" with "dotfiles". The two are synonyms in this project and the long form misleads, because *shared* suggests sharing between people and this system is built for one. [Dotfiles](../decisions/014-dotfiles.md) carries it in its context and in two of its arguments, and [Installation Checks](../development/007-installation-checks.md) in the check that says the operator would be able to read the shared configuration and change none of it.
- Take a dotfiles package from a `git` origin and from a `tar` origin at least once. Only `local` has been exercised. The `git` one matters most: it is the only origin cloned with its history, because `/dotfiles` stays the repository [Disk Layout](../decisions/001-disk-layout.md) restores from, and that the history and the remote survive the copy into the target has unit coverage and nothing else.

## Tools Pending Specification

- `**oparch-network-manager**` — wifi and wired network manager.
- `**oparch-pacman**` — browser across pacman repositories and package installer.
- `**oparch-secret-export**` — writes the local dotfiles secret store out as one encrypted archive. The installer takes such an archive as an input when the dotfiles map declares secrets, so it is how a machine gets its credentials before first boot without every token being typed at the console. The archive is meant to travel on a removable medium or from a URL, which is what its encryption has to hold up. What it is encrypted with, and whether restoring a store is this tool or a second command, are part of its specification.

## Issues

- The netboot binary on the EFI system partition is copied once, during installation, and nothing refreshes it afterwards. [Installer Inputs and Bootstrap Baseline](../tools/oparch-installer/002-inputs-and-bootstrap-baseline.md) puts `/EFI/OpinionatedArch/netbootx64.efi` there from `/usr/share/ipxe/x86_64/ipxe-arch.efi`, but when pacman later updates `ipxe` the copy stays at whichever build the installation took. So the external recovery path that [Bootloader](../decisions/008-bootloader.md) requires ages in place, and it ages unnoticed: it is the path used when the machine is already broken, which is the moment it is first exercised. The drift is older than the package it now comes from — the download it replaced never tracked its source either, and left nothing on the machine to refresh from. What is new is that the source is now installed on the target, so the copy can be refreshed at all, and [Boot Image Format](../decisions/007-boot-image-format.md) decides that a pacman hook on `ipxe` is what refreshes it, with the installation writing it only the first time.
- A successful installation shows red lines that mean nothing went wrong. The log paints `Said::Complaint` red, and a complaint is defined as whatever a command wrote to standard error — but writing to standard error is not how a program says it failed, it is where plenty of them put everything that is not their output. `mkinitcpio` reports possibly missing firmware there, and `grub-install` announces `Installing for x86_64-efi platform.` and `Installation finished. No error reported.` there too, so the end of a run that worked is a column of red. The rule to fix is `stderr means failure`, not any one command. Painting complaints yellow and leaving red to `Said::Failed` is a line and is most of the truth; colouring them by the exit code of the command that produced them would be the whole of it, and costs more, because the lines are pushed as they stream and the code is not known until after the last one.
- There are two ways to run a command. A caller either calls the shell port directly, or calls `run_in` with a target, and nothing says which is meant where: the installer uses `run_in` because it works on a system it is not running on, and the tools that only ever work on their own machine call the port. One way would be for `run_in` to be the only door and the port's `capture` to be the primitive that only it calls, so that every command says where it runs and a tool that later gains a second root changes what target it passes rather than needing every call found. It is not urgent — no tool is at risk of running a command against the wrong root today — and the cost is one argument at every call site.
